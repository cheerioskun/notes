We want to run the experiment from Part 1: five calls to do_work, five entries counted, and five returns counted. The application should still produce the same results. This part installs bpftime and runs that experiment.

First, follow the two programs we launch. The loader prepares the BPF programs and reads their counters. The target runs the original application with bpftime’s agent library inside it.

Two launches, two preloaded libraries

A shared library is a file of compiled code that can be loaded into a program. On Linux these files commonly end in .so. The dynamic linker is startup code that finds and loads the libraries a program needs.

LD_PRELOAD is an environment variable that asks the dynamic linker to load an additional library when it starts a dynamically linked program. bpftime uses it to put its code into each of our two processes.

The bpftime command-line tool wraps this mechanism for the common workflow. In the first terminal, bpftime load launches your loader with the syscall-server library. In the second, bpftime start launches the target with the agent.

The loader in this lab is a C program using libbpf, a library for loading and attaching BPF programs. Ordinarily those loading operations go to the kernel. The preloaded libbpftime-syscall-server.so handles the supported operations through bpftime instead. Despite its name, this “server” is library code inside the loader.

The other library, libbpftime-agent.so, goes inside the target. It opens the shared experiment state, prepares the BPF programs, and uses Gum to install their function hooks.

The command named load takes an executable loader command. In this example loader opens probe.bpf.o. Passing the BPF ELF object itself as though it were a native executable confuses two different build products.

A description becomes a live hook

The agent must turn the loader’s request into something executable in this process. It opens the existing shared memory, prepares the requested BPF programs and their helpers, finds the target function, and asks the selected hooking library to install the hook.

The startup functions in bpftime’s source

The agent’s entrypoint is bpftime_agent_main. On the glibc preload route, its replacement for __libc_start_main arranges to call that entrypoint before the application’s original main. The agent opens shared memory with SHM_OPEN_ONLY and calls init_attach_ctx_from_handlers to prepare and connect the requested programs, maps, and attachments.

On Ubuntu, this startup path uses the GNU C library, called glibc. bpftime’s wrapper establishes the order bpftime_agent_main → original main. It does not establish that every kind of application initialization happens after agent setup. Constructors and library startup have their own ordering, and hooks can fire during initialization in other workloads. Our lab’s first do_work invocation is deliberately in main, after the wrapper has run.

The target also has to find the function in its own memory. A compiled file’s code can be loaded at different addresses in different runs. The loader therefore describes a location in a binary or library; the target determines where that location sits in its own address space. This avoids assuming that an address observed in the loader means the same thing in the target.

Where is the loader script executed?

In this lab there is a C loader executable, not a script. If you use a script to launch it, the shell executes that script outside the target. The native loader performs libbpf operations in its own process. The target executes the injected agent and BPF probe; it does not replay your loader script.

What changes with late attachment?

bpftime attach PID injects the native agent into an existing process and invokes its entrypoint. The target has already passed main startup, so the preload wrapper is not how the agent gets control. It still needs access to compatible shared state and still must prepare and install the requested hooks.

Injection permissions depend on ownership and the host’s ptrace/security policy. A successfully injected library is only one milestone; it does not prove that a symbol resolved, a BPF program prepared, or a hook fired. For a first run, use preload and a small dynamically linked C target. Static binaries and managed runtimes need their own startup and calling-context treatment.

Install a deliberately small function-hook build

The lab targets Ubuntu 24.04 Linux, x86-64 or ARM64, with a dynamically linked C application. Use a Linux VM or container if your development machine runs another OS. Two terminals must share that same Linux environment; two independent containers do not automatically share the required memory namespace.

This recipe uses LLVM, a compiler toolkit, to translate the BPF programs into native code for the target CPU. It builds the CPU function-hook components; it does not install the optional syscall-transformer or GPU path. Selecting the execution engine matters: one engine can reject instructions that another supports. Our probe uses an atomic add.

Keep the source/build tree: the lab links against its libbpf and uses its headers. clang -target bpf needs a Clang distribution that includes the BPF backend; Ubuntu’s package does. CMake downloads matching Frida development archives, so network access to upstream release assets is also required.

Verified November 4, 2026: built the pinned upstream revision with LLVM on Ubuntu 24.04 ARM64, compiled this lab, and ran both CLI launches. The plain target left counters at zero; the hooked target preserved all five results and reached entries=5 returns=5. The loader exited cleanly. The dependency-install line was reviewed against the build requirements; a fresh OS installation and x86-64 execution were not tested.

The plain target prints its PID and five results: 1, 4, 7, 10, 13. nm confirms that the target contains a named function. objdump shows its original instructions on your architecture. Neither tool shows the live patch merely by reading the executable on disk.

Now open two terminals in this same lab directory. The commands set BPFTIME_VM_NAME=llvm to choose the BPF execution engine and BPFTIME_GLOBAL_SHM_NAME to name the shared experiment state. Use a shared-memory name dedicated to this exercise in both. Stop the loader before starting a fresh experiment with another name.

Wait for Registered do_work entry + return and initially zero counters. That output says the loader registered its requests. The target has not executed a probe yet.

Terminal 2 prints the same five function results. Terminal 1 should eventually show entries=5 returns=5. Intermediate snapshots can differ because reads happen while the target is running. Running another target while the loader stays alive adds five more calls.

There are three different compiled files in this experiment. The target and loader are ordinary CPU executables. probe.bpf.o contains BPF instructions and map definitions; it needs bpftime to execute its programs. This .o uses the ELF file format, which lets a compiler package code together with names and other information that a loader can read.

The source files have corresponding jobs:

Read the loader: names become attachment requests

The complete loader checks errors and keeps links alive. These are the calls that connect its inputs to the objects discussed in Part 1:

open_file reads the compiled BPF file and identifies its programs and map definitions. load issues map/program operations that the preloaded server handles. Program lookup selects C function names in the BPF object. The attach calls separately select the target binary/function and entry versus return behavior. The map lookup selects counts for the loader’s polling loop.

In the BPF source, SEC(".maps") places the map definition in the ELF section libbpf expects. __uint and __type describe map properties and key/value types through type metadata. SEC("uprobe") and SEC("uretprobe") identify program conventions; they do not replace the loader’s explicit binary/function attachment request.

Whose calls do these counters count?

The attach calls pass pid = -1: this lab requests no specific PID. A matching target needs its agent, access to this namespace, and a resolvable module/function attachment before its calls contribute. An ordinary unpreloaded target does not join the experiment just because it runs the same executable.

The two map entries are shared aggregate counters for this experiment, not one map per target. Multiple participating targets or threads add to the same values; the atomic increment prevents concurrent increments from overwriting each other. Separate process/thread attribution requires keys that encode that identity. The two totals also do not correlate individual invocations or prove argument handling. This lab does not test PID-specific filtering.

To hook your own C function, use a target with a suitable non-inlined symbol, change .func_name = "do_work" in the loader, rebuild, and pass the correct target binary path. Restart the loader and then launch your target with the agent. If your probe reads arguments or return values, use the correct register/context layout for the target architecture; our counter intentionally avoids that extra dependency.

Locate the missing stage

Debug this as a chain of milestones. “The loader started” and “the target printed output” are each compatible with a probe that never ran.

ObservationNext thing to inspect
Clang rejects -target bpfCheck clang --version and clang --print-targets. Use the Ubuntu BPF-capable compiler, not a different host compiler on PATH.
Loader attempts kernel loading / fails with permissionsConfirm it was launched through bpftime load or with the syscall-server preloaded. Ordinary libbpf without that interception follows its kernel path.
Agent cannot open shared memoryStart the loader first. Match BPFTIME_GLOBAL_SHM_NAME, user/access permissions, and container/IPC environment.
Attachment cannot resolve or patch the functionCheck nm -n ./target, the exact binary path, the agent’s diagnostics, inlining, stripping, and an entry too short for the backend.
Target runs; counters remain zeroRead $HOME/.bpftime/runtime.log for agent/program errors. For visible diagnostics, set BPFTIME_LOG_OUTPUT=console in the loader terminal before starting it. On a longer-lived target, inspect /proc/PID/maps for the agent. A library mapping alone still does not prove hook installation.
Results belong to an older experimentStop this lab’s loader and target. Use a new dedicated shared-memory name in both terminals. Avoid deleting another experiment’s live shared state.

For a live target, gdb -p PID followed by disassemble /r do_work inspects the in-memory instructions, subject to debugger permissions. Compare them with objdump on disk. That answers a different question from inspecting BPF bytecode with llvm-objdump -d probe.bpf.o.

For research, first prove that your event fires and original behavior survives. Then measure the plain target, empty probes, and the real extension with matched builds and workload. Keep logging outside the timed event path. A five-call correctness check is not an overhead benchmark.

The call, with its history restored

The loader opened an object and recorded an attachment. Startup put a native agent in the target. The agent realized those descriptions as executable probe code and a live hook. Then an ordinary call followed a local detour, updated shared state, and returned its original result. The observer printed that result’s evidence later.

The same five calls still return the same five results. We have added two BPF programs that count what happened around them.

For a small next experiment, change the return BPF program to immediately return 0;. Rebuild, stop the old loader, and restart both commands with a new shared-memory name in both terminals. The expected final counts become entries=5 returns=0. The application’s five results should remain unchanged. When you introduce a native helper, a different runtime, or a new attachment backend, identify the new boundary before carrying your old assumptions across it.
