A program calls do_work(). You want to count those calls. You have the executable, an idea for a probe, and a reason to keep the application’s source untouched.

This series assumes you know C function calls and Linux processes; it introduces the BPF-specific pieces as they become necessary. For a runnable starting point, jump to Part 3’s installation and lab.

Imagine comparing two instrumentation policies in a service you cannot rebuild for every run. You want the application binary held constant while you replace the probe, reuse BPF compilation and map interfaces, and observe what happens at the same function boundary. The counter is our smallest version of that experiment; it establishes the execution path before adding a research policy.

Linux already has a way to do this: attach an eBPF program to a uprobe. bpftime changes where that probe program executes. To understand the system, start with one call crossing—or staying on one side of—a boundary.

The same call, a different place

An eBPF program is a small program compiled to BPF instructions. A runtime supplies its execution engine, its event context, and callable operations called helpers. Linux can provide that runtime in the kernel. bpftime provides a runtime in userspace.

With a conventional kernel-backed uprobe, the application reaches an instrumented instruction and traps into the kernel. The attached BPF program executes there, then execution returns to the application. This is a privilege transition within the event path; it need not mean scheduling another process.

bpftime’s ordinary Frida-Gum function hook redirects execution through a runtime loaded into the application. The BPF program runs as part of the calling thread’s detour. The runtime can interpret BPF instructions or JIT-compile them to the processor’s native instructions.

That is the architectural move: put the probe’s execution machinery in the process that reaches the event. The question now is how to give that process a program, a place to keep results, and a route into the runtime.

The observer and the observed

Our example has two executables. The target calls do_work() five times. The loader opens a BPF object, requests entry and return probes, then periodically prints two counters. “Loader” here means an ordinary userspace program using libbpf, the library commonly used to load BPF applications.

The BPF object is a third build product: an ELF file containing BPF instructions and map definitions. It is neither of those two executables.

A map is the BPF programming model’s named data structure for storing state. Our array map has two entries: key 0 counts function entries; key 1 counts normal returns. The loader reads it; the probes update it.

The loader needs a library too. libbpftime-syscall-server.so intercepts supported BPF loading and attachment operations and represents them in bpftime. Despite “server” in the name, this library runs inside the loader process; our example starts no separate server daemon.

The target loads libbpftime-agent.so. That library contains the runtime and uses an attachment backend to install the redirect. Shared memory is how it finds the loader’s descriptions and the map data. The agent prepares process-local execution objects and executable code from that state.

The distinction to keep

Preparing an attachment in the loader and patching a live function in the target are different events. Shared descriptions connect them; they are not the same operation.

Once the hook is installed, each call takes a local detour through the target’s runtime. The loader’s polling loop is a separate activity. There is no request to the loader asking it to execute BPF for every call.

What exactly runs at the event?

The entry probe in our downloadable lab is deliberately small. It looks up a counter and increments it. The same operation with key 1 runs at normal function return.

ctx is the context supplied by the hook. This probe does not inspect it. bpf_map_lookup_elem is a helper call: the BPF program asks the runtime to find a map entry. The runtime supplies a native implementation in the target process.

A JIT translates the BPF computation into native code; it does not move that computation into the loader. Likewise, a BPF helper call is not automatically a syscall. These are three separate concepts: the BPF operation, its native implementation, and any OS operations that implementation uses.

What does moving execution buy?

Keeping function-probe dispatch in userspace can remove the kernel trap from this event path and enables extensions to use in-process capabilities through supported helpers. That makes bpftime interesting when frequent events or runtime extensions are part of a systems experiment.

The cost changes with the hook backend, callback, BPF program, helpers, build, and machine. “Userspace” alone does not establish a speedup. A useful experiment compares an uninstrumented baseline, empty BPF probes, and the actual probe on the same workload. Here “empty” means the same entry and return attachments and execution engine, with BPF bodies that immediately return and perform no map operations. A bare Gum callback would isolate a different cost.

There are also good reasons to choose another route. If you own the application and can rebuild it, a direct native call may be simpler. If you need kernel events or cannot inject a library into the target, kernel eBPF may fit better. Familiar libbpf interfaces do not make every kernel program type, helper, verification guarantee, or isolation property available in bpftime. Our Part 3 build leaves the optional standalone verifier disabled and does not load the probe into the kernel for verification. A userspace execution engine and a verifier are separate components.

A probe participates in the application

Probe work adds to the event’s latency. A native helper executes with the process’s capabilities and can affect its state. Code that waits, allocates, takes locks, or calls back into a managed runtime needs a separate execution-context argument. The BPF language alone does not make those operations harmless.

We can now place every component. What we have not explained is the decisive step: an ordinary call still targets do_work(). How does it reach the probe?
