The target is about to call do_work(4). The agent is already loaded, the BPF program is ready, and the function entry has been instrumented. Follow this one call until it returns.

We will stay on the ordinary Frida-Gum entry/return path. Installation comes in Part 3. Here, “where does execution go next?” is the only clock.

The call still names the original function

An ordinary native call branches to a function and preserves a route back to its caller. A hook can leave that call site alone and change what happens when execution reaches the function’s entry.

Frida-Gum is a native instrumentation library. bpftime uses its interceptor API from C/C++; this path does not require a Frida JavaScript script or a JavaScript engine. Gum installs an entry redirect and preserves displaced instructions in a trampoline: a small piece of executable code that makes the detour and continuation possible.

The ldr loads 0x0000ffff9db29000 into x16; br x16 redirects execution there. The two words at +8 and +12 are address data, so a linear disassembler can misleadingly decode them as invalid instructions. The displaced stack adjustment and register operations must still execute through the relocated path. The destination address changes across runs; the pattern shown is one observed Frida choice, not a universal patch layout.

The displaced instructions still matter. Skipping a prologue instruction could lose a stack adjustment or register save. Copying instruction bytes blindly can also fail when an instruction uses a PC-relative address. Gum’s relocator preserves the instructions’ meaning at their new location.

This is why an extremely short or unsupported function can be hard to hook. For a first experiment, use a real, non-inlined function with a discoverable symbol. Our lab compiles do_work at -O0 and marks it noinline.

Stay with the calling thread

The injection mechanism may involve other threads, and the resident agent may have background maintenance work. Those facts do not move this ordinary synchronous probe invocation onto a worker thread. Its computation is on the intercepted thread’s path.

Which stack?

The native interception callbacks execute as part of that thread’s native call path. BPF also has a defined stack/register model, realized by its execution engine. Calling a helper crosses a BPF-to-native interface; it does not create another process or automatically hand work to another scheduler.

Return probes add invocation bookkeeping and a leave path. They should not be modeled as a second independent patch at every ret. Normal return is our example’s completion condition. Exceptions, nonlocal jumps, process termination, and recursion require additional reasoning before you use entry/return pairs to manage resources.

What a helper call really crosses

The BPF program cannot directly link an arbitrary C++ library just because it runs in userspace. A helper is an exposed operation with a defined calling convention. bpftime registers a native implementation; the VM or JIT routes the BPF call to it.

bpftime also has a user-function mechanism, commonly called ufunc, for registered native functions. To use a new native operation, you must supply its implementation, make it available in the target, register the interface, and ensure it is ready before a probe calls it. Loading a BPF object alone does not perform all of that work.

The practical consequence is larger than the API detail. A helper that blocks delays the intercepted thread. A helper that takes an application lock can encounter locks already held at the hook point. A native callback into a language runtime must respect that runtime’s stack, ABI, and scheduling requirements. “Same process” establishes access; it does not establish a safe calling context.

Our counter extension uses built-in map helpers and needs no custom agent modification. Keep that first success separate from the larger task of deploying a new native helper.

Next boundary: expose your own native operation

A raw helper and a ufunc are distinct interfaces. A raw helper registers a native implementation at a BPF helper ID. A ufunc registers a function in a separate registry; BPF calls the dispatcher helper with that function’s ID and an argument list. Choose an existing built-in helper when it provides the operation; use a deliberate native integration when it does not.

For a small pinned example, read the native add-function registration test, then its BPF caller and UFUNC_CALL declarations. The native side uses ebpf_ufunc_func_info and bpftime_ufunc_register_ufunc; the BPF side uses UFUNC_CALL_2 through the dispatcher.

This upstream example is an in-process runtime test, not a complete injected-agent deployment. To deploy the same idea, put the native implementation and registration in the target-side runtime integration—for example a deliberately modified agent—and rebuild that native artifact. Register it in the runtime instance that will execute the BPF program, enable the ufunc helper group (enable_ufunc_helper_group in the runtime configuration), and establish readiness before installing or firing the probe. Adding registration only to the separate loader does not supply the target’s native function pointer.

A different event: the syscall instruction

Optional side trip. This is a second interception mechanism, not a prerequisite for the function-hook lab. You can continue to installation and return here later.

Function entry is one useful place to intercept execution. Another is the instruction that requests a syscall. On Linux x86-64, the syscall number is passed in rax. zpoline exploits that convention to create a compact redirect.

The original syscall instruction is two bytes, 0f 05. An indirect call *%rax is also two bytes, ff d0. The rewrite can replace one with the other without growing the instruction sequence.

Address 1 is useful only because setup maps executable trampoline code near address zero. The syscall number becomes a landing address in a NOP-filled region; execution moves through that region into the common hook path. The hook recovers the request, runs its policy or probe, and can forward the operation through a preserved real syscall instruction.

bpftime’s x86-64 text-segment transformer implements this style of rewrite and connects the syscall hook to its dispatcher. bpftime start -s selects the transformer route. It is a different startup path from the function-only preload route used in our lab.

The kernel still handles a forwarded syscall

Intercepting write lets userspace observe or override the request. If the hook forwards it, execution still enters the kernel to perform the write. The probe’s location and the operation’s final implementation are different questions.

Mapping page zero can be restricted by the OS. The zpoline path described here is x86-64-specific; it is not an ARM64 function-hook requirement. An ordinary LD_PRELOAD wrapper for libc’s write also has different coverage: it sees calls through the wrapped symbol, while instruction rewriting targets syscall sites in the code being transformed.

We have now followed the two kinds of detour. One redirects a function entry; the other redirects a syscall instruction. Neither explains how the descriptions became a working runtime inside the target. For that, rewind to startup.
